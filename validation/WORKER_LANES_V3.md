# 需求对话与正式研究的固定任务槽

## 本次修复的具体瓶颈

旧 `claimResearchTask()` 在任意 `ResearchTask.status = running` 时拒绝领取其他任务，执行循环又等待整个正式研究完成。需求对话因此可能直到一轮长研究结束后才开始调用模型。

本次只增加一类固定的需求对话执行槽，不开放任意研究并发，不改变模型调用预算：

| 对象         | 固定上限   | 判定                                     |
| ------------ | ---------- | ---------------------------------------- |
| 正式研究任务 | 全局 1     | `preset != intake` 且 `status = running` |
| 需求对话任务 | 全局 1     | `preset = intake` 且 `status = running`  |
| 研究模型调用 | 仍为全局 2 | 原 `budget.ts` 的容量预留与计数逻辑      |

`claimResearchTask(lane?)` 仍使用同一个 PostgreSQL transaction advisory lock。在该事务内检查对应类别的运行计数、选择排队任务、写入唯一 `executionToken` 与心跳/截止时间。不同进程争抢同类任务也只有一个领取者。无参调用保留兼容性，选择当前可用类别中最早的排队任务；一个已被占用的研究槽不会让队头研究任务挡住后面的需求对话。

## 执行和退出合同

- 一个 worker 内有两个受控执行循环，每个循环一次最多执行一个任务。全局上限由数据库领取事务保证。
- 每个 worker 实例共用一个维护节奏，失联恢复每次维护执行，文件清理每小时执行；两个执行循环不会各自再启动一套全量维护。
- worker 心跳及维护任务被明确等待。任务自己的心跳也只允许一个数据库写入在途，退出时等待最后一次写入结束。
- SIGINT / SIGTERM 或任一受监督循环抛出异常，会中止两个活动任务并等待两个执行器完成清理，再断开 Prisma。
- 如果退出发生在领取事务尚未返回时，返回的任务仍交给已取消的执行器进行终态提交。执行器在准备资料或进入阶段前检查取消信号，不开始上游调用。
- 正常退出中的任务标记为 `interrupted`。已有正文和资料保留，仍未明确结束的调用标记为 `unknown`；任务不会自动重新排队。
- 取消、完成、失联恢复仍沿用任务行锁和 `executionToken` 校验。旧执行器即使晚到，也不能覆盖显式重试后新持有者的结果。
- 强制杀进程无法等待清理；此时继续依靠原有 60 秒失联判定与显式重试流程。

维护节奏是**每 worker 实例共用**，没有新增全局维护 leader。多实例的领取上限是真正全局的；清理仍使用原有文件锁，恢复仍使用原有任务锁与 token 检查。

## 需求阶段不读取附件

`executeResearchTask()` 仅在 `!sourceTaskId && preset !== 'intake'` 时执行 `prepareResearchInputs()`。需求对话使用已有需求文字和已选聊天上下文，不在每轮确认中重复调用文档抽取、整理图片或登记网页证据。正式研究启动后按原有流程读取已经上传的资料。

界面和模型提示应说明：附件已收到，但需求确认尚未分析附件内容。这个阶段不能声称已经理解图片、PDF、Word 或链接中的事实。

## 仍然存在的延迟边界

独立任务槽消除“必须等正式研究完成才能领取需求问题”的阻塞，不能保证模型立即获得调用容量或立即返回。

按活动任务记账的全局模型调用容量仍为 2。实际 GPTR 适配配置的 `DEEP_RESEARCH_CONCURRENCY` 为 1，但依赖内部对子问题存在 `asyncio.gather`，不足以证明整个研究过程只会占一个模型调用槽。如果两个模型槽正在使用，需求对话仍由原 `waitForResearchCall()` 等待容量，不会额外发出未经预留的调用。

这里的任务上限指数据库中的有效运行所有权。显式取消或失联后，已送达外部服务的请求是否及时停止，依赖现有取消传播和上游实现；不能仅凭数据库终态宣称外部执行已经结束。旧执行权被阻断、不自动重跑与不重复记账的合同继续有效。

本次未修改 `budget.ts`，未增加第 3 个模型槽，未增加付费模型调用或上游自动重试，也未把等待期伪装成持续出字。

## 定点验收

### 调度与退出：6 项离线测试

文件：`lib/research/worker-lanes.test.ts`。本轮实际执行通过，进程退出码为 0。

```bash
pnpm exec vitest run --config vitest.research.config.ts lib/research/worker-lanes.test.ts --reporter=verbose
```

覆盖：两类同时执行且每类串行、退出等待两个任务、一个循环失败后联动停止、在途领取返回后只做中断收尾、维护与心跳不重叠且等待清理、已取消的 worker 不启动任何工作。

### 真实 PostgreSQL：6 项定点集成测试

文件：`lib/research/worker-lanes.integration.test.ts`。必须通过原 `scripts/test-research.mjs` 在一次性 `chugao_research_it_<随机值>` 数据库中执行。普通离线运行会跳过这组，不应将跳过算作通过；本次运行结果见整包的最终验收记录。

```bash
# 使用本地测试 PostgreSQL 地址。脚本会创建、迁移并最终删除独立数据库。
RESEARCH_TEST_DATABASE_URL='postgresql://<本地测试账户>@127.0.0.1:<端口>/<测试维护库>' node scripts/test-research.mjs
```

覆盖：运行中的研究不阻塞 intake、同类多领取者竞争和两类总上限、取消后只释放对应类别且拒绝旧写入、两次并发恢复只产生一次中断并保留片段、显式重试后旧 token 无效、领取期间退出时两任务均中断且不调用上游、需求对话不做附件抽取而正式研究仍走原准备入口。

集成测试直接建立合成队列行，只验证调度与执行权，不把直接建行当作绕过服务端需求确认约束的合法 API。每项测试只清理自己创建的 project 子树，不截断或改写其他测试数据，不接触生产数据库，也不实际调用模型或外网。

## 代码入口与部署边界

- `lib/research/worker-lanes.ts`：两个执行循环、失败监督与等待退出。
- `lib/research/worker.ts`：全局领取、共享维护、执行器终态和附件准备条件。
- `workers/research.worker.ts`：信号处理与数据库退出顺序。

无需新增数据库字段或迁移。部署时需要用同一版本更新 worker，确认旧 worker 已退出；混跑旧版会保留旧版“遇到任意 running 任务就不领取”的行为，无法保证体验改善已经生效。在途任务仍按现有明确中断与重试合同处理，不自动重跑。
