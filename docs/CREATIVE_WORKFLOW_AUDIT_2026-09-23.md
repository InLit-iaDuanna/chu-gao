# Chugao Studio 辅助创作工作流：代码审查与第一版实施清单

日期：2026-09-23。审查对象：当前本地工作树，不代表已经复核生产部署版本。

后续进展：本地已加入第一版辅助创作入口，详见 [辅助创作模式实现说明](ASSISTED_CREATIVE_MODE.md)。下文保留本次审查时的记录；部分保护仅在新模式启用，不能据此认为普通生图流程的问题已全部解决。

## 结论与边界

沿用 Next.js、TypeScript、PostgreSQL、BullMQ、Zod 和 Sharp。先完善一次创作操作的提交、执行、结算和版本关系，再增加结构化需求整理与图片标注，不引入新的 Agent 框架。

本轮完成代码审查，以及提交补偿、参考图计价和来源图顺序的局部修复。**这不是辅助创作第一版的完整实现，也没有消除所有重复调用风险。**

没有修改数据库结构或业务数据，没有启动 Worker，没有请求真实生图，没有同步服务器；原有用户改动保留。

## 本轮已修复

### 1. P1：队列接受后写库失败可能覆盖执行状态并误退款

位置：`lib/generations.ts` 的 `createAndEnqueueGeneration`。

原逻辑把 Redis 入队和之后写回 `jobId` 放在同一个 `try` 中。任一步出错，都会无条件把任务改成 FAILED，并按预计积分退款。任务如果已经被 Worker 领取、完成，或已由另一条路径退款，可能被覆盖或重复退款。

修复：

- 在创建事务内保存确定的 `jobId = generation.id`，提交后再入队，不再进行入队后的任务编号写回。
- 入队报错时先做条件更新，只允许本次仍未执行的任务转 FAILED：PENDING、执行令牌为空、尝试次数为 0、心跳为空、任务编号匹配。
- 条件更新成功后，在同一事务里按生成扣款减已有退款计算可退金额；金额为 0 不写退款。
- 若执行、取消或恢复已经先行改变任务，返回现有任务状态，不覆盖，不再次退款，也不再发起一个生成。
- 失败补偿写入 `finishedAt`。

限制：这保证的是本次队列补偿不会覆盖已执行任务，不等于 HTTP 提交具备幂等性。数据库整体不可用、客户端丢失响应等情况仍需下面的操作幂等与对账设计。

### 2. P2：使用历史图片时可能选错定价规则

位置：`app/api/generations/route.ts` 的 POST。

原逻辑先计算价格和价格快照，再把 `sourceImageIds` 解析为参考图。只使用历史生成图时，`usesReference` 被计算为 false，可能命中文生图价格，而不是后台配置的参考图价格；报价、余额校验和结算快照都会受影响。

修复：完成参考图权限校验、解析和总数校验之后，再计算价格和快照。上传图、历史图和两者混用都以完整参考图集合计价，不修改后台价格规则或历史账单。

### 3. P2：来源图片顺序依赖数据库返回顺序

位置：同一 POST 的来源图片查询。

SQL 的 `IN` 查询不保证与输入 ID 顺序一致。现在查询带回图片 ID，再按照 `sourceImageIds` 排序；上游请求与保存的参考图列表保持一致。继续拒绝缺失、无权访问或重复的来源 ID。

限制：这只保证当前接口内上传图组、来源图组各自的既有顺序，不代表已经实现跨组自由排序、参考图角色或显式基图锁定。

## 尚未解决的风险

### 4. P1：生图 POST 会自动重试，不能保证一次确认只提交一次上游生成

证据：

- `lib/http.ts:15` 的 `PROVIDER_FETCH_RETRY` 配置 4 次重试；`fetchWithTimeout` 对配置的 HTTP 状态和网络异常重试。
- `lib/providers/openai-images.ts:259`、`:292` 的编辑和生成 POST 使用该重试配置。一次适配器调用最多可能发送 5 次 HTTP 请求，不是承诺一定生成或收费 5 次。
- `lib/providers/index.ts` 在部分错误后还会切换账号或渠道。
- `workers/generation-worker-recovery.ts:109` 默认把失去心跳的 RUNNING 任务重新入队。执行令牌能防止旧执行结算，却不能撤销已经到达上游的付费调用。

影响：超时、断连、网关错误并不必然代表上游未接受任务，盲目重发可能重复消耗上游额度。现有用户侧账本保护不能替代上游调用去重。

待改：按阶段记录未提交、提交中、已接受、结果未知和终态；付费 POST 默认不自动重试未知结果，只在上游明确保证未受理或支持幂等键时使用经过验证的重试策略。查询状态、下载结果与重新生成分开。不同协议和账号池必须采用一致策略，不能只关掉某个适配器的重试。

### 5. P1：客户端提交没有持久化幂等键

证据：`app/api/generations/route.ts`、`lib/generations.ts`、`prisma/schema.prisma:265`。目前没有提交操作 ID 和对应唯一约束。`components/studio/StudioApp.tsx` 的发送锁只覆盖当前组件实例。

影响：响应丢失后再次发送、另一个标签页发送或重复 API 请求，可以创建两个 Generation、两条扣款记录。BullMQ 的 generationId 只能去重同一个任务，不能识别两次 HTTP 请求其实是同一用户操作。

待改：客户端每次确认产生稳定操作 ID；服务端建立用户范围内唯一约束和请求摘要。同一 ID、相同内容返回原任务；相同 ID、不同内容返回冲突。检查应先于可能已变化的价格、余额和容量条件，避免合法重放被拒绝。模型不能自行创建新的付费操作 ID 绕过确认。

### 6. P1：恢复任务可能丢失历史参考图

证据：`workers/generation-worker-recovery.ts:127` 从 `paramsRaw` 重建请求；`lib/models/validate.ts:174` 只把 `referenceImageKeys` 转为内部参考图，未解析 `sourceImageIds`。恢复函数虽然查询了最终 `Generation.referenceImageKeys`，但没有用它恢复完整参考集合。

影响：原本是历史图片续改，恢复后可能变成无图生成，或仅保留上传图。计价快照仍可能保留图生图价格，导致请求内容与收费依据不一致。

待改：保存并恢复经过授权解析的完整、排序稳定的请求快照。恢复时重查文件可用性和权限，不允许缺图后悄悄转成纯文字生图；不可恢复就明确终止或请求用户重新选择。此改动需与执行阶段和安全重试一起验证。

### 7. P2：对话续改缺少锁定约束和显式版本关系

证据：`components/studio/StudioApp.tsx:372` 默认取最近成功生成的第一张图片；`prisma/schema.prisma:232`、`:265`、`:314` 没有工作区当前采用版本、父版本或参考图角色字段。`app/api/conversations/compile/route.ts` 的编译结果只有提示词、短回复和是否生成。

影响：多轮编译依赖聊天摘要，不能可靠保证道路宽度、坡度等用户要求始终保留；也不能把“本次基于哪张图、改哪里、保留什么”作为稳定的业务状态审计。当前单任务 UI 限制减轻了并发影响，但不能替代版本模型。

待改：持久化可编辑的创作简报和版本；分别记录保留项、修改项、禁止项和用户锁定项。每次确认固定基图 ID、简报版本和有序参考角色；迟到的生成结果只新增候选版本，不自动覆盖用户已经采用的版本。

### 8. P2：auto 的实际尺寸计费尚未在当前结算代码兑现

证据：`workers/generation-worker-settlement.ts:53` 使用提交时单价快照乘成功张数；`lib/model-pricing.ts:137` 不接收实际尺寸。返回图宽高写入 GeneratedImage，但没有参与该价格计算。日志中的 `auto_actual_size` 名称不能证明实际尺寸已参与计价。

待改：先明确按提交时价格规则计算实际尺寸的结算规则和用户授权金额上限，再补完整定价规则快照与测试。不能用结算当时后台可能刚修改的价格追扣，也不能未经用户授权无限补扣。本轮未调整历史账单、渠道价格或积分余额。

## 已有机制应保留

- 建任务、对话消息、余额扣减、扣费日志在同一数据库事务中完成；余额使用条件扣减。
- 每用户事务锁让任务数量检查与创建串行。
- 生成结果通过执行令牌和 RUNNING 条件完成结算，旧执行无法随意写入终态。
- 失败结算、恢复终止已有按账本剩余金额退款的保护。
- 上传图路径和历史生成图查询均检查归属。
- 当前取消接口只允许取消 PENDING，不应改成“中止浏览器请求就宣称上游生成已取消”。

## 第一版实施顺序

| 阶段              | 具体修改面                                                                     | 验收条件                                                                                       | 当前状态 |
| ----------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- | -------- |
| A：局部安全修复   | 提交补偿、历史图计价、来源顺序、回归测试                                       | 队列确认丢失不覆盖执行状态；参考图价格、快照、余额校验一致                                     | 本地完成 |
| B：操作与执行状态 | Generation 幂等字段或独立操作表、API、前端提交客户端、Worker、适配器、恢复任务 | 并发重复提交只创建一笔任务及扣款；未知上游结果不盲重发；恢复不丢图；旧令牌不能继续发起付费调用 | 待实施   |
| C：简报与版本     | 创作简报版本、锁定项、基图及父版本、采用版本指针、编译接口                     | 修改一个要素不悄悄丢掉锁定项；选择旧图续改始终基于旧图；迟到结果不切换当前版本                 | 待实施   |
| D：标注与质检     | 原图及坐标标注分开保存、变换坐标、受限图像检查、失败说明                       | 标注后原图不被覆盖；缩放后位置一致；检查最多一次；不自动发起质量重绘                           | 待实施   |

B 阶段需做只增不删的数据库迁移，旧记录的新字段允许为空，保留旧工作流；通过功能开关逐步开启。迁移失败不得清空历史数据。上线前分别验证普通生图、历史图续改、PPT 和节点入口，因为它们可能共用任务创建逻辑。

第一版只允许用户每次确认的一次生成操作和确认张数，不开放模型自主增加图片数量、选择更贵渠道或连续重绘。标注只是语义引导；只有接口明确支持并验证了 mask 时，才提供具有对应边界承诺的蒙版编辑。
